One pathway, four apps: EMR, CCIS, Studio, Marketplace

The EMR and CCIS already hold most of the parts. What is missing is a shared contract that lets a pathway travel: authored in the Studio, published to a marketplace, filled in as a form in the EMR, and analysed in CCIS. This plan names the contract, the build order and the decisions that need you.

The idea, as I read it

Contextual element

A small, versioned, reusable definition of something recorded about a patient (vitals, eGFR, HbA1c, onset time). It declares type, unit, time meaning and which states count as "unknown" or "not collected".

Pathway

A designed set of elements, with an order. The EMR entry form is a pathway: basic EMR today, then DM, CKD and DM+CKD. This is the unit that gets designed, published and reviewed.

Trajectory

What actually accumulates for one patient when elements and pathways are applied in whatever order real care takes. It is the unit of analysis. It is keyed by concept (for example creatinine), not by which form it was typed into.

Analytics and rules

Analytics bind to elements, so they work on any pathway that contains those elements. Rules are published with a pathway and run inside the EMR form.

Check my reading of "trajectory". You wrote that elements make pathways as a set, and used randomly they make a trajectory. I took that to mean design time versus use time: the pathway is designed, the trajectory emerges. If you meant something else, section "Pathway package" is the part that changes.

Gaps that block your design

  • Two meanings of "pathway". In the EMR a pathway is a list of element sets. In CCIS a pathway has stages, decision nodes and analytics references. Neither describes the entry form layout, composition, or rules.
  • Two element models. EMR fields have id, label, type, unit, options, repeat. CCIS fields add cardinality, time semantics, epistemic states, source classes and a terminology binding. Nothing converts between them.
  • No concept key on observations. The EMR keys values by (element set, field key). Two sets that both hold creatinine give two unrelated series, which breaks trajectories and DM+CKD.
  • Condition contexts are hard-coded. context-map.js lists diabetes, CKD and hypertension set slugs by hand. A published pathway should declare this instead.
  • CCIS has no element-group or rule artefact. The spec requires element groups (CCIS-REQ-023, 024) but no schema exists. Rules are not in the standard at all.
  • Guardrails point against rules. EMR set definitions may not hold numbers or bands, CCIS parameters with a threshold default to disabled, and a pathway may not automate a high-impact action (CCIS-REQ-027). Rule intelligence needs its own governed path (section "Rule intelligence").

Architecture

Everything that travels is a checksummed artefact in the marketplace. Patient data never goes there; it moves only between the EMR and CCIS as a context envelope and a run record, as it does now.

Design rules that hold the four apps together

  • Compose by reference, never by copy. A DM+CKD pathway points at the DM and CKD elements by exact version. Because analytics bind to elements, an analytic written for the CKD elements runs on CKD and on DM+CKD without being rewritten.
  • The CCIS artefact is the source of truth. The EMR builds its element sets and pathway versions from the published artefact and stores the source id, version and checksum.
  • Marketplace content is local-review content. Pathways pulled into the EMR arrive as submitted drafts and go through the EMR's existing review rules, the same way imported questionnaires and bundles already do.
  • No server for the Studio. Build it as a static app like CCIS (single hashed script, strict CSP) that reuses CCIS's validator, compiler and market code. Publishing produces a market folder change for a pull request.

The new field facet is the concept key. It is what lets eGFR typed in a CKD form and eGFR typed in a DM+CKD form land in one trajectory, and it is how CCIS recognises "the same data" across pathways. Composition: DM, CKD, DM+CKD

  • DM and CKD are authored once each, from the tier 2 elements plus the tier 1 core.
  • DM+CKD is a composed pathway: a new package that references both, with no copied fields. This is the "element group" the CCIS spec already requires. The Studio produces a conflict report: shared concepts (creatinine, eGFR, blood pressure, HbA1c) are matched by concept key, never by similar label (CCIS-REQ-024), and the author picks which element owns each shared field.
  • In the EMR, applying DM and then CKD to one case produces the same form as applying DM+CKD: shared fields appear once and one value series is kept.
  • An analytic that needs eGFR and HbA1c is compatible with DM+CKD but not with DM alone. Compatibility is therefore a catalogue-time check on elements, run before any patient data is involved.

What each app does and what changes

EMR Enhancer

Pathway-driven entry form rendered from entryForm. Marketplace import into a staging table (pattern of migration 033), then the existing review workflow. Hard-coded DEMO_PATHWAYS replaced by imported packages. New migration: concept key on observations and source artefact id, version and checksum on element set versions. Trajectory view uses concept keys and package-declared contexts. Rule runner for approved rule packs.

CCIS

Static compatibility between an analytics package and a pathway: the existing checks without data readiness. Catalogue filtered by pathway. Pull analytics from the marketplace through the existing remote loader. First real analytics beyond snake for DM, CKD and DM+CKD, using the planned templates (trend, monitoring gap, follow-up due). Run on the trajectory, not only a single envelope, comes with Phase 5.

Studio

Same stack as CCIS. Screens: element catalogue, pathway composer with conflict report, analytics attach and compatibility view, rule builder, validate (eight layers) and test fixtures, publish bundle. Reuses the CCIS SDK builders and the governed AI-draft gate. New repo needs scaffold, CI and the CSP build.

Marketplace

A third repo with the existing folder format. CI runs the CCIS validator and checksum check on every pull request. Releases are immutable. Index gains a pathway-to-analytics lookup so apps can list compatible items without opening every file.

Rule-based intelligence in the EMR

This is the highest-risk part. The repos currently forbid numbers in element sets, keep clinical thresholds disabled, and say a pathway must not authorise treatment. A rule pack must respect that, so it needs its own artefact type and its own review path.
  • Rule pack artefact. Rules written in the same three-valued whitelist expression language the CCIS executor already uses (18 operators, unknown never becomes false or zero). No code, no network, no clock.
  • Two classes. Data-quality rules (missing, stale, conflicting, inconsistent entries, interval documentation) can ship first. Clinical prompts (anything with a clinical threshold) stay blocked until a named clinician owns them.
  • Thresholds are parameters, disabled by default, enabled locally by a clinician, with the enabling recorded.
  • Output is a visible prompt that shows its rule id, version and the records it read. Never an order, never a silent change of data.
  • Review independence. The author of a rule pack is never its reviewer (the CCIS governance plan already states this rule). Each fire is logged in the EMR next to the audit log.

Decisions that need you

  1. Is my reading of "trajectory" right? (section "The idea").
  2. Clinician owner. Still unnamed in the CCIS plan. Without one, DM and CKD analytics and any clinical rules stay as demonstrations of mechanics, with thresholds disabled.
  3. Marketplace host. A GitHub repo with static hosting fits the existing format. Confirm the repo name and who may merge.
  4. Studio stack. I recommend static and serverless like CCIS. This also keeps the open D-002 decision (no shared server) intact. Say if you need multi-user editing early, which would change it.
  5. CCIS source of truth. Confirm that published CCIS artefacts, not EMR sets, are authoritative for pathways.
  6. Rule scope for the first release. Data-quality rules only, or also clinical prompts under a named owner.
  7. Terminology. Stay on local codes for the standard element list, as decided on 25 Nov 2026.
  8. Naming. "CCIS" is a working name per its plan, to settle before any public release.
  9. Concept ownership. Confirm one owner element per concept, with other elements referencing it.
